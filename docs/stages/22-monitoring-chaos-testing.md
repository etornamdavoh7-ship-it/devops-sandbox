# Stage 22: Chaos Testing & Incident Response

## Goal
To validate our alerting pipeline by intentionally crashing the database, simulating a real-world production outage.

## What We Did (Phase 4)

### 1. The Chaos Injection
We simulated an EC2 instance failure by stopping the database container:
```bash
docker compose stop mongodb
```
Simultaneously, we simulated user traffic attempting to load the site using a bash `while` loop that curled the API once every second.

### 2. The "No Data" Gotcha
Initially, Grafana triggered a system alarm: `[FIRING:1] DatasourceNoData`.
* **The Root Cause:** Because the `http_requests_total{status_code="500"}` metric had literally zero data (no 500 errors existed yet), Prometheus returned a blank result. Grafana's default behavior is to panic when it receives "No Data", assuming the monitoring agent itself is broken.
* **The Fix:** We updated the Alert Rule's evaluation behavior. We changed **"Alert state if no data or all values are null"** from `NoData` to `Normal`. This tells Grafana that having zero 500 errors is a good thing, not a broken thing.

### 3. The Real Incident
Once Prometheus scraped the flood of 500 errors generated by our `curl` loop, Grafana officially resolved the `DatasourceNoData` panic and evaluated our actual rule.
After the 1-minute pending period, it successfully routed the following payload to Slack:
`[FIRING:1] Database Crash (500 Errors) Prod Alerts`

### 4. The Resolution (Self-Healing)
To restore service, we ran:
```bash
docker compose start mongodb
```
Because our `curl` loop was still running, the application immediately re-established the database connection. The API stopped throwing 500 errors and began returning `200 OK`. Grafana detected the drop in error rate and automatically dispatched a `[RESOLVED]` notification to Slack, officially closing the incident.
